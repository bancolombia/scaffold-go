Naming and validation

The CLI rejects invalid names before it writes files. Rules live in internal/validator/validator.go.

Summary​

WhatRuleExample validExample invalid
Project name (init)^[a-z][a-z0-9-]*$blog-serviceBlog, 1svc, My_App
Component name (entity, usecase, ep, da)^[A-Z][a-zA-Z0-9]*$User, CreatePostuser, create-post
Field namePascalCase, Name:typeEmail:stringemail:string, Email
Directory for initMust not already existnew folderexisting path

Project names​

scaffold-go init my-service
scaffold-go init my-service --module github.com/acme/my-service

If --module is omitted, the module path equals the project name (init.go).

Component names​

Used by entity, interface, usecase, ep http, ep consumer, da api, da publisher, and da cache:

User          ✓
CreateUser    ✓
User2         ✓
user          ✗ must start with uppercase
create_user   ✗ no underscores

HTTP handlers: if the name ends with Handler, that suffix is stripped before generation (UserHandler → User).

Fields​

Format Name:type, comma-separated. Repeatable via Cobra string slices (-f a:string -f b:int also works).

scaffold-go generate entity Order \
  --fields UserID:string,Total:float64,CreatedAt:time.Time

Supported in practice: any Go type string you pass through. time.Time triggers a time import on the entity template (entity.go generator). The validator only checks Name:type shape and PascalCase names — it does not whitelist types.

Dependencies and use cases​

FlagShapeExample
--dependenciesname:TypepostRepo:IPostRepository
--usecasesname:Type or name:Type:PackagecreatePost:CreatePostUseCase
--routesMETHOD:path:handlerPOST:/posts:CreatePost

Use-case dependency types are imported from internal/domain (usecase.go.tmpl). Prefer domain interfaces (IUserRepository), not adapter structs.

Project must be initialized​

generate * fails unless a go.mod exists in the current or a parent directory:

project not initialized: no go.mod file found ...
Run 'scaffold-go init <project-name>' first
